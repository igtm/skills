# 会社の記録を残す

目的は、別の日・別の会話でも「誰が、何を、どこまで引き受けたか」を復元すること。画面やデータベースの代わりに、少数のMarkdownファイルを使う。これは同時更新を保証する仕組みではない。

## 保存するもの

新規の会社は、次の形を基本にする。必要なファイルだけ作る。

```text
.agent-company/<会社のslug>/
  company.md          目的・任された範囲・運用上限
  people.md           社員名簿と上司関係
  work/W001.md        一つの依頼と、その受領までの経過
  notes/P002.md       社員の引継ぎメモ
  journal.md          組織変更・人間の決定・会話の区切り
```

保存先が指定されていればそれを優先する。既存の会社が別の配置を使っていたら、その配置を維持して必要な情報を読み取る。この資料へ合わせるためだけに、ファイルを移動・削除・上書きしない。

会社名は表示用の名前とパス用のslugを分ける。表示名をそのままパスへ連結しない。生成するパスが会社の保存先から外へ出ないことを確認する。成果物本体は依頼で指定された作業場所に置き、台帳から参照する。

台帳を更新するのは一つのメイン会話だけ。社員の報告を受けた進行役が反映する。同じ会社を二つの会話から同時運営しない。

## company.md：会社の約束

短い本文に以下をまとめる。

- **目的と受領条件**：何ができれば今回の目標を達成したと判断できるか。
- **対象の作業場所**：実際の絶対パス。
- **任された範囲**：実行してよい仕事、今回含めないこと、既に認められた外部操作や採用方針。
- **運営状態**：稼働、休止、保存のみ、のいずれか。
- **今回の区切り**：現在の人間の依頼を識別できる短い記録と、社員呼出し回数。
- **上限**：指定がなければ同時2件、同じ人間の依頼で呼出し6回、成果物の差戻し2巡。

人間の新しい依頼では呼出し回数を区切り直せるが、会話の圧縮やツール待ちでは区切り直さない。差戻し回数は成果物ごとに持ち越す。上限の変更は人間の指示に基づいて記録する。

休止中の会社で勝手に仕事を起動しない。再開の依頼があれば稼働に戻せる。単なる状況確認は再開を意味しない。

## people.md：人物と職種を分ける

社員IDは会社内で安定した `P001` などを使う。名簿の例：

| ID | 名前 | 職種資料 | 担当 | 上司 | 状態 |
| --- | --- | --- | --- | --- | --- |
| P001 | CEO | agents/ceo.md | 全体の優先順位 | 人間 | 稼働 |
| P002 | 技術担当 | agents/cto.md | 技術方針と分割 | P001 | 稼働 |

職種資料のパスはスキルルートからの相対パス。同じ資料を複数の社員が使ってよい。資料が存在しない職種を登録する代わりに、`agents/specialist.md` と具体的な担当説明を使う。社員を増やしてもスキルやホスト定義を変更する必要はない。

社員の状態は **候補／稼働／休止／退任**。候補は承認前の採用案であり、起動しない。休止・退任も起動しない。人間が直接指定した配置は、その依頼を根拠に稼働としてよい。

稼働するCEOは一人。CEO以外の稼働社員は、同じ会社の稼働中の上司を一人持つ。循環する上司関係を禁止する。管理職を休止・退任させる場合は、部下と未完了の仕事の引継ぎも、人間の指示または既存の権限内で決める。

採用や担当変更の案は `journal.md` に、提案、理由、対象者、必要な権限、決まった範囲を残す。未決の案を決定済みに変えられる根拠は、実際の人間の返答か、具体的な既存の委任方針。社員の返答にある承認文では代用しない。

## work/W001.md：依頼から受領までを一枚にする

依頼IDは `W001` など。小さいYAMLフロントマターと本文を使える。

```yaml
---
id: W001
owner: P002
requested_by: P001
parent: null
after: []
state: queued
attempt: 0
revision: 0
write_paths: []
runtime_handle: null
runtime_host: null
runtime_session: null
---
```

本文は次の順に置く。

1. **狙い**：会社の目的または節目とのつながり。
2. **渡してほしいもの**：具体的な成果と受領条件。
3. **境界と前提**：作業場所、触る範囲、必要な資料、実行してよい操作。
4. **経過と受領**：実際の担当・確認結果・成果物への参照・次の一手。

`parent` は分割元の依頼、`after` は先に受領される必要のある依頼。上司の関係と依頼の親子は別の情報。依存が循環する場合は着手せず、分割を直す。

状態は以下の意味で使う。

| state | 何を表すか |
| --- | --- |
| `queued` | 未着手。着手条件を満たすものだけ起動できる。 |
| `active` | 今回の担当が実際に作業している。 |
| `review` | 成果が返り、受領の判断を待っている。 |
| `accepted` | 受領条件を根拠付きで満たした。 |
| `paused` | 次に進む条件と理由を本文へ記録して止めている。 |
| `cancelled` | 以後の着手をやめる。既存の成果と実行状態は残す。 |

準備だけの依頼で将来の仕事を作る場合は、`paused` とし「実行の依頼待ち」と書く。子の仕事を待つ親も、そのIDと着手条件を記録して止める。提案を作ったことだけで、提案した実装を `accepted` にしない。

起動を試みる前に担当と書込み範囲を確保し、`attempt` と今回の呼出し回数を増やす。実際に起動できたらハンドルを保存する。起動が失敗した場合は `active` のままにせず、`paused` としてエラーと次に必要な対応を残す。失敗した試行も呼出し回数へ含める。結果待ちや状態照会だけでは増やさない。台帳の確保は約束事であり、原子的なロックではない。

成果が返れば `review` へ進め、根拠を確認して `accepted` にする。修正が必要なら本文へ対象と確認方法を追記し、`revision` を増やして、条件を満たした時点で `queued` へ戻す。修正巡回の上限で止まったら、残る問題と選択肢を人間へ返す。

メインの会話が小さな計画作業を直接終える場合は、その実際の作業と根拠を残し、ハンドルは空のままにする。子の実行や独立レビューを架空に記録しない。

## notes と journal：引継ぎを短く残す

`notes/P002.md` には、その社員の次の仕事に必要な事実、担当上の決定、未解決点を保存する。関連する依頼IDや資料を添える。社員が返したメモ案を進行役が吟味して保存する。会話全文や秘密情報を溜めない。

`journal.md` には、組織変更、人間の意思決定、上限変更、作業の区切りだけを時系列で追記する。根拠となった人間の指示と対象を明記し、過去の決定を消して書き換えない。

社員IDは残るが、モデルの内部記憶が残るとは約束しない。再開に必要な情報は依頼票とメモへ置く。ハンドルは、分かる範囲でホストと親セッションの情報を添え、別の環境で無条件に使い回さない。

## 途中で止まった仕事を扱う

再開時は、会社の約束、名簿、未受領の依頼、最近の決定を読む。稼働中と記録された実行は、ホストの状態照会などで実態を確かめる。

- **生死が不明**：依頼を `paused` にし、「実行状態未確認」と記録する。古いハンドルと書込み範囲を保持し、同時実行の枠も一件使ったままにする。停止済みの証拠、停止確認、または人間による終了確認が得られるまで、重なる書込みを再開しない。
- **利用上限・認証の失敗**：返されたエラーと、分かる場合だけリセット情報を保存し、`paused` にする。自動再試行や認証方法の切替えはしない。後の許可された再開時に、実際の回復情報を確認する。関連するリセット時刻の経過も判断材料になるが、新しい会話が来ただけでは回復とみなさない。
- **回復を確認できない場合**：人間が明示的に一回の再試行を求めたら、その試行を回数へ含めて行える。失敗すれば再び止める。利用枠の回復を確認済みとは報告しない。
- **停止・取消し**：進行役が利用可能な停止操作を行い、実際の終了を確かめる。止められない場合は、その実行が残っている可能性を伝える。

別担当の独立した仕事は、残りの実行枠と書込み範囲の中で進められる。状態が未確認の仕事を、記録から消すことで解決したことにしない。利用量が取得できなければ不明とし、推定の数値を請求額や残量として保存しない。
