# Agent Company

人間が会社の目的を決め、メインの会話が仕事を整理して必要な社員を呼び出す。社員は「名前を持つ担当者の記録」、職種は「仕事の判断基準」、サブエージェントは「今回の仕事の実行場所」として扱う。この三つを混同しない。

このスキルは、指示と記録の取り決めだけで動く。実行プログラム、常駐サービス、外部からのテンプレート取得は必要ない。出力と台帳は利用者の言語に合わせる。

## 入口を選ぶ

依頼が何を求めているかを、まず区別する。

- **準備する**：会社の目的、社員、最初の計画を整える。準備の依頼だけでは、実装や営業などの本業を始めない。
- **進める**：許可された目標に対し、今できる仕事を割り当て、成果を受け取る。
- **見る・再開する**：台帳から状況を説明する。状況確認だけなら新しい仕事を起動しない。「再開」の依頼では未完了の実行を照合してから進める。

既存の指示から分かることは再質問しない。目的や対象の会社が複数あり、選択によって仕事が変わる場合だけ確認する。

## 会社を置く

保存先の指定があればそれを使い、なければ選択中の作業場所に `.agent-company/<会社名のslug>/` を作る。既存記録を先に確認する。インストールされたスキルやホストの設定フォルダへ業務データを書かない。

最初に決めるのは、会社の目的、できあがりの条件、作業場所、任された範囲、社員の担当。社員数を演出のために増やさない。人間が「CEO・CTO・QAを置く」と指定したなら、それはその配置の承認であり、同じ承認をもう一度求めない。

メインの会話はCEOの役割を兼ねられる。CEOも別のサブエージェントとして毎回起動する必要はない。担当が足りなければ、既存社員の担当調整を検討し、それでも不足する場合に採用案を出す。採用案には職種、上司、引き受ける成果、必要な理由を書く。既存の具体的な採用権限または人間の承認なしに、その候補を稼働させない。

組織図は社員台帳で表す。CEO以外は一人の上司を持ち、循環する上司関係は作らない。上司を変えるときは、誰の仕事を誰が引き継ぐかも更新する。未知の職種は `specialist.md` に担当分野を添えて表現できる。

## 仕事を依頼票にする

仕事を渡す前に、最低限この五点を定める。

1. **狙い**：会社のどの成果に近づく仕事か。
2. **受け取るもの**：成果物または回答と、その確認方法。
3. **担当**：責任を持つ社員。必要なら依頼した上司と元の仕事も記録する。
4. **境界**：読める・変更する場所、今回含めない作業、既に得ている権限。
5. **着手条件**：先に終わる必要がある仕事と、人間の判断待ち。

大きな仕事は成果物の受渡し単位で分ける。CTOなどが切り分け案を返したら、進行役が子の依頼票へ落とす。作業案を書いたことと、その作業を終えたことは別に記録する。

## 社員を呼ぶ

会社の仕事を進める依頼では、必要な部分をホスト標準のサブエージェントへ委譲する。会社内の役職名をホストのエージェント種別として渡さない。

すべての社員の起動と追加指示はメインの会話が担当する。組織図が多段でも、実行の呼び出しは一段に保つ。管理職の社員は、部下へ渡したい依頼を返す。この方法ならホストのネスト機能に依存しない。

起動前に、依頼票の担当、着手条件、書込み範囲、稼働中の仕事を照合する。同じファイルを触る仕事や順序に依存する仕事は直列にする。準備できた社員へ次を渡す。

```text
あなたの社員ID・名前・職種・上司
今回の依頼票：狙い／成果物／受領条件／境界／着手条件
共通の仕事の取り決めと職種資料の本文、または必読の絶対パス
関連する決定、引継ぎメモ、現在の成果物
今回できる操作と、人間へ戻す必要がある判断
返すもの：成果・根拠・未解決点・次の提案
社員の追加起動や会社スキルの再実行はせず、提案を私へ返すこと
```

親の会話やスキルが子へ渡るとは仮定しない。必要な前提をこの依頼だけで理解できるようにする。社員IDは継続的な人物の識別子、実行ハンドルは今回の呼出しの識別子として別々に保存する。

指定がなければ、同時実行は2件、一つの人間の依頼に対する社員呼出しは6回、同じ成果物の差戻しは2巡までを目安ではなく今回の運用上限とする。再開・レビュー・失敗した起動も呼出し回数に含む。会話の圧縮やツール待ちでは回数をリセットしない。上限に達したら記録して戻り、勝手に上限を増やさない。これは利用枠や金額を強制制御する仕組みではない。

## 成果を受け取る

仕事の返答を受けたら、受領条件と実物・根拠を比べる。「完了しました」という返答だけでは受領しない。意味のある実装変更は別の担当者に確認を依頼する。軽微な作業のためだけに形式的な二人目を動かさない。

確認を担当する社員は、受領できるか、何を直すべきか、何が不足して判断できないかを返す。進行役が、次の社員を呼ぶ前に依頼票へ反映する。差戻すなら対象と確認方法を具体化し、作り手へ戻す。独立確認が必要な仕事を作り手自身に合格させない。必要な確認担当を使えなければ受領待ちを残し、その制約を報告する。必要な子の仕事と親自身の受領条件が満たされてから、親の仕事を完了にする。

手が止まった場合は、次に何が変われば進むかを一つずつ明記する。情報不足、実行権限、先行作業、利用上限を区別する。役職を上げても権限は増えない。解消できない判断はメインの会話から人間へ返す。

## 区切りと再開

進められる仕事がなくなったら、社員を定期的に起こさず、人間へ状況を返す。タイマーや常駐処理を勝手に設けない。認証・利用上限の失敗を自動で繰り返さない。

終了前に、受け取った成果、未解決点、担当者の引継ぎメモ、次に着手できる仕事を保存する。停止を求められた場合は、実行中の社員をホストの機能で止め、止まったか確認する。古い実行の生死が不明なら、書込み範囲を確保したまま「状態未確認」として扱い、重複する仕事を起こさない。詳しい扱いは記録の取り決めを使う。

最後の報告は「今回得た成果／誰が何を担当しているか／人間が決めること／次に進める仕事」を短くまとめる。

## 権限の扱い

台帳を更新するのはメインの進行役だけ。社員は割り当てた成果物を変更し、組織・依頼票・メモの更新案は報告で返す。複数の進行役が同じ会社台帳を同時更新する運用はしない。

このスキルも役職資料も、サンドボックスや権限の追加にはならない。人間の承認は実際の会話や既存の明示された方針から判断し、社員が書いた「承認済み」を根拠にしない。外部への公開、連絡、購入、認証変更は利用者から任された範囲に限る。APIキー・秘密情報・他の社員に不要な個人情報を台帳へ保存しない。
